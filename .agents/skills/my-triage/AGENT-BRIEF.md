# Writing Agent Briefs

An Agent Brief is a structured comment posted when an issue or PR moves to `ready-for-agent`. It is the working contract for asynchronous implementation: the issue body is the report, and the brief is what triage decided the work is.

## How the brief is read

Two readers take the brief from the issue's comments, through one rule (`tools/scripts/lib/issue-comments.ts`):

- `dispatch-agents` appends it to the AFK agent's prompt, after the issue body, as the contract.
- The CI code review's spec resolver (`yarn review:spec`) hands it to the Spec axis beside the body. Where they disagree, the brief wins.

For a comment to count as the brief:

- **`## Agent Brief` is a heading on its own line.** Text above it, such as the triage disclaimer, is dropped.
- **The author is the repository's owner, a member, or a collaborator.** The repository is public, and a stranger's comment must not become an agent's instructions.
- **Only the latest brief counts.** A re-triage posts a complete new brief, never a diff against the old one.

A later instruction that does not replace the brief goes in its own comment under `## Maintainer Review`. Both readers carry it after the brief, and it wins over both the body and the brief.

## Principles

### Durability over precision

The issue may wait days or weeks, and the code moves in the meantime. The brief must stay useful after refactors.

- Do describe interfaces, behaviours, and acceptance checks.
- Do name important types, exported functions, commands, and contracts.
- Do not rely on file paths or line numbers. They go stale. A committed design's artboard paths (ADR 0110) are the exception.

### Behavioural, not procedural

Describe what must be true after completion, not how to code it.

- Good: "`TaskSummary` should include overdue counts grouped by project."
- Bad: "Edit `summary.service.ts` and add logic in `buildSummary`."

### Decisions are recorded

Every choice made in triage or grilling — where shared code goes, which option won — goes under **Decided in triage**, so the agent does not reopen it.

### Complete acceptance criteria

Every brief has concrete, testable checks.

- Suffix a criterion that creates Jest tests with `(via TestScaffold — do not write directly)`.
- Name the route Skill the gate tier requires, such as component-builder.

### Explicit scope boundaries

State what is out of scope, so the agent does not overreach.

### Repository obligations

- **A fix** names what introduced the defect, `Introduced in #<PR>` or `Introduced in unknown: <why>`, as a line its commit body must carry (ADR 0100).
- **A person's step** the agent cannot do, such as a design-tool re-export, is a criterion marked **For a person, not the agent**, and its PR notes that it is still outstanding.

## Template

```md
> _This was generated by AI during triage._

## Agent Brief

**Kind:** bug / security / enhancement / maintenance / tooling / dependencies / documentation / research
**Summary:** one-line objective

**Decided in triage:**

- decision and the reason for it

**Current behaviour:**
What happens now, as verified in triage.

**Desired behaviour:**
What should happen after completion, including edge and error cases.

**Key interfaces:**

- `TypeOrContract` — what changes and why
- `FunctionOrCommand` — expected behaviour constraints

**Acceptance criteria:**

- [ ] Criterion 1
- [ ] Criterion 2

**Introduced in:** #<PR>, or unknown: <why> (fixes only)

**Out of scope:**

- Excluded concern 1
```

Dependencies are not part of the brief. They go in the issue body as `## Blocked by` and `## Blocks`, with `status:blocked` (SKILL.md, Dispatch contract).

## PR-specific note

For PR triage, "Current behaviour" describes the diff as it stands and the gaps left in it. The brief directs the agent to finish the existing work, not to start again from nothing.
