# My Triage

MyOrganiser's own triage Skill. It keeps the triage concept from Matt Pocock's `triage` skill ([mattpocock/skills](https://github.com/mattpocock/skills)) — a small state machine of roles, a verified claim, and a durable Agent Brief — and adds what this repository's agents need to act on a triaged issue: kind labels that pick the right branch type, the dispatch labels `dispatch-agents` filters on, and dependency edges it can read. Credit for the state machine and the brief format is his; the dispatch contract is ours.

A triaged issue is finished only when an agent can pick it up. A brief with the right state role but no dispatch labels is invisible to `yarn dispatch-agents --all-standalone`, and is not done.

Every comment or issue body posted during triage must start with:

```md
> _This was generated by AI during triage._
```

## Roles

**Kind** — exactly one kind Surface Label (`tools/config/github-labels.json`), picked by what the work _does_. It is the category role, and it decides the branch type (AGENTS.md, Branch naming), so it must not contradict itself:

| The work                                 | Kind            | Branch   |
| ---------------------------------------- | --------------- | -------- |
| Fixes broken behaviour, wrong docs       | `bug`           | `fix/`   |
| Fixes a vulnerability                    | `security`      | `fix/`   |
| Adds or changes product behaviour        | `enhancement`   | `feat/`  |
| Refactor, cleanup, dead code, test noise | `maintenance`   | `chore/` |
| Agent tooling, scripts, checkers         | `tooling`       | `chore/` |
| Dependency change                        | `dependencies`  | `chore/` |
| Missing docs (not wrong ones)            | `documentation` | `docs/`  |
| Investigation                            | `research`      | `docs/`  |

Remove any other kind label the issue already carries. The branch type takes the first match top to bottom, so a refactor still labelled `enhancement` gets a `feat/` branch. Area labels (`web-app`, `backend`, `mobile-app`, `github-actions`) stay.

**State** — exactly one of `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, or closed `wontfix`.

The orchestrator moves an issue from `ready-for-agent` to `ready-for-human` itself when a standalone run finishes with a passing gate (ADR 0138): its branch is waiting for a person to review it and open the PR. Its latest comment names the branch. Move it back to `ready-for-agent`, with a `## Maintainer Review` comment, only to send it to an agent again.

`qa` and `grilling` are orchestration labels, not states (ADR 0049). Remove `grilling` once the grilling is done.

## Invocation

Maintainers invoke `/my-triage` in natural language:

- "Show me things that need attention"
- "Let's triage #42"
- "Move #42 to ready-for-agent"
- "What is ready for agents?"

## Show what needs attention

Present these buckets, oldest first, with counts and one line per item:

1. Unlabelled items (never triaged).
2. `needs-triage`.
3. `needs-info` with reporter updates since the last triage notes.
4. **Not dispatchable:** `ready-for-agent` issues that break the dispatch contract below — no `type:*`, `complexity:*`, or `gate:*`, more than one kind label, or no `## Agent Brief` comment.
5. **Ready to unblock:** `status:blocked` issues whose every `## Blocked by` issue is closed.

If PR triage is enabled, include in-scope external PRs and tag each row `[PR]` or `[issue]`. Then ask what to triage next.

## Triage a specific issue or PR

1. **Gather context.** Read the whole thread — body, comments, labels, author, dates — and any earlier triage notes before asking anything. For a PR, read the diff and its review comments. Check whether the behaviour already exists, and check `.out-of-scope/*.md` for an earlier rejection of the same idea.
2. **Verify the claim** against the current code, not the report's file names: files move. For a bug, reproduce it from the reporter's steps. For a PR, check the claim against the diff and its tests. Report the result as confirmed, failed, or not enough detail. For a fix, look for what introduced the defect: its brief must name it (ADR 0100).
3. **Check for overlap** with other open issues: two issues that rewrite the same code are folded into one, and work that must land after another issue gets a dependency edge.
4. **Grill when needed.** If the requirements are fuzzy, run `/grill-with-docs` and `/domain-modeling`.
5. **Recommend** the kind, state, and dispatch labels, with reasons, and wait for the maintainer's direction.
6. **Apply the outcome:**
   - `ready-for-agent`: post the Agent Brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)), then apply the dispatch contract below.
   - `ready-for-human`: post the same brief, saying why an agent should not do it. Add no `type:*` label: `ready-for-human` is not dispatched.
   - `needs-info`: post the triage notes template below.
   - `wontfix`: close it with the reason. If it is already implemented, point to where. If it is a rejected enhancement, update `.out-of-scope/` ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)), link it, and close. If it is a rejected bug, explain and close.
   - Folded into another issue: close it as `not planned` with a comment naming the issue that absorbs it, and carry its scope into that issue's brief.

## Dispatch contract

`dispatch-agents` sweeps only the open issues labelled `ready-for-agent` **and** `type:afk` that carry none of `type:hitl`, `status:blocked`, `status:in-progress`, or `prd`, and that have no `PRD: #` line (those are PRD slices, which belong to `to-issues`). An issue moved to `ready-for-agent` gets all of the following:

| Label or section                                                       | Rule                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type:afk` or `type:hitl`                                              | `type:afk` when an agent can finish it alone. `type:hitl` when a person must act part-way through, before an agent can finish. A person's step after the merge, such as a design-tool re-export, is a brief line for the PR, not HITL.  |
| exactly one `complexity:low` / `complexity:medium` / `complexity:high` | Selects the model. `low` is a single-surface edit with an obvious shape. `medium` is behaviour across a few files. `high` is a design choice inside the work, crypto or vault, or cross-library reasoning.                              |
| exactly one `gate:mechanical` / `gate:standard` / `gate:full`          | From [`.claude/checklist.md`](../../../.claude/checklist.md) Step 0. When unsure, promote. The orchestrator treats a missing label as `gate:standard`, so a mechanical issue must say so.                                               |
| `## Blocked by` / `## Blocks`, appended to the **issue body**          | Only when the work must wait for another issue. Each dependency is a list item that **starts with** the issue (`- #1302 — rewrites the same hook`). Keep both directions: edit the blocker's body to list this issue under `## Blocks`. |
| `status:blocked`                                                       | While any `## Blocked by` issue is open. A standalone run does not clear it; once every blocker has merged and closed, remove it (bucket 5 above finds these).                                                                          |

The dependency sections go in the body because that is where the orchestrator looks for them (ADR 0002). The brief stays a comment.

Before moving on, check that the issue is selected:

```sh
yarn dispatch-agents --all-standalone --dry-run
```

An issue that should be dispatched but is not in the plan has broken the contract. Fix the labels; never change the orchestrator's filter to fit.

## Quick state override

If the maintainer explicitly asks to move an item to a state ("move #42 to ready-for-agent"):

1. Confirm the label changes, the comment, and any close or reopen.
2. Apply exactly what they asked for, plus the dispatch contract when the state is `ready-for-agent`.
3. Skip grilling.
4. If it has no Agent Brief, ask whether to draft one now. Without one, an agent works from the report alone.

## Needs-info template

```md
> _This was generated by AI during triage._

## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Make each question specific and actionable.

## Resume behaviour

When an item already has triage notes:

1. Read the earlier notes first.
2. Check whether its open questions were answered.
3. Present the updated status.
4. Do not ask again what is already resolved.
5. When the decisions change, post a **complete** new Agent Brief. Readers take only the latest one, so a brief that says "as above, plus …" loses everything above.
