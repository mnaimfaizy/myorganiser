# Web Vault Agent Guide

## Scope

Browser vault implementation using WebCrypto and web storage/client sync helpers.

## Commands

- Test: `yarn nx test web-vault`.
- Lint: `yarn nx lint web-vault`.

## Do

- Keep plaintext only in client memory while unlocked.
- Store and sync encrypted blobs for every Vault Blob Type in `VAULT_BLOB_FIELDS` (`src/lib/vault/vaultBlobFields.ts`). That table is the list; do not restate it here.
- Fan out over the blob types by iterating `VAULT_BLOB_TYPES` and indexing `VAULT_BLOB_FIELDS`. Do not hand-enumerate members in an object literal, an if-chain, a union, or a run of `if` statements — `yarn enum:fanout:check` fails it ([ADR 0053](../../../docs/adr/0053-a-fan-out-over-a-domain-enum-is-pinned-at-its-call-site.md)).
- Converge a Vault Blob through `convergeVaultBlob` (`src/lib/vault/vaultConverge.ts`) — it is where a convergence decision belongs, and writing a second one is the mistake this rule exists to stop. Every caller is wired: the sync sink drains through it (`vaultSyncQueue.ts`), the pull check does (`vaultPullCheck.ts`, scheduled by `vaultPullTrigger.ts`), and so does the sign-in pass (`vaultReconcile.ts`). Reconcile still visits every pinned type, but it reads the Vault Blob Inventory first and GETs a type only when the inventory says its Ciphertext differs from this device's Sync Bookmark — a type the inventory does not name is not read, and absence is never a deletion ([ADR 0087](../../../docs/adr/0087-a-vault-pull-pass-asks-the-vault-blob-inventory-and-absence-deletes-nothing.md)). How each type converges is pinned in `VAULT_BLOB_CONVERGE_STRATEGIES` in `libs/vault-core/src/lib/records/vaultBlobConverge.ts`, shared with the mobile Vault Push; add the strategy there, not a branch at a call site ([ADR 0054](../../../docs/adr/0054-a-vault-blob-converges-by-record-and-absence-is-recorded.md), [ADR 0107](../../../docs/adr/0107-a-mobile-vault-write-is-read-modify-write-against-the-server.md)). `vaultBlobFields.ts` re-asserts that table against `Record<VaultBlobType, …>` beside `VAULT_BLOB_FIELDS`, which is where `yarn enum:fanout:check` pins it.
- Check for what changed elsewhere through `createVaultPullTrigger` (`src/lib/vault/vaultPullTrigger.ts`) — it debounces the mount/focus triggers and stops for good the first time a check finds the Session gone (401/403). A pass reads the Vault Blob Inventory first, conditionally, and asks about a Vault Blob Type only when the inventory says its Ciphertext differs from this device's Sync Bookmark, which includes a type this device holds no bookmark for — that is how a type created on another device is discovered. A type the inventory does not name is neither read nor written: absence is nothing to pull, never something to delete. A failed inventory read fails the pass and records every type unanswered; there is deliberately no fallback to asking each type in turn, because a path that runs only when something is already wrong is a path nothing exercises ([ADR 0087](../../../docs/adr/0087-a-vault-pull-pass-asks-the-vault-blob-inventory-and-absence-deletes-nothing.md)). The per-type read is still a conditional GET carrying that type's Sync Bookmark ETag as `If-None-Match`; a 304 costs no work and touches nothing local.
- Write an array-shaped Vault Blob from a page through `saveVaultRecords` and delete a record through `deleteVaultRecordAndSave` (`src/lib/vault/vaultRecordWrite.ts`), never with `saveEncryptedData` and a bare array. A bare save drops the Deletion Log another device wrote, and a filtered-out record is not deleted — the next merge with a copy that still holds it brings it back ([ADR 0054](../../../docs/adr/0054-a-vault-blob-converges-by-record-and-absence-is-recorded.md)). Stamp `updatedAt` on every edit, or the edit loses to a deletion it came after.
- Gate a merge on decrypting the server's copy, never on Vault Meta equality. A passphrase change rewraps the same Master Key, so meta differs while every Vault Blob stays readable.
- Refuse a take across a differing Vault Identity, which is the one thing about a Vault Meta a Vault Blob decision may read. `convergeVaultBlob` takes the pass's observed server Vault Meta as a **required** parameter and reads only the Vault Identity from it, through the same pinned facet `vaultMetaConverge.ts` reads (`vaultIdentityOf`) — so "two Vaults" has one definition. The guard sits above the clean/dirty branch, refuses rather than asks, and needs no Master Key, so it holds while the Vault is locked. This is not the merge gate the rule above forbids: it answers whether the two sides are the same Vault at all, before merging is a question ([ADR 0067](../../../docs/adr/0067-a-vault-blob-is-never-taken-across-a-vault-identity.md)). Supply the meta once per pass; convergence runs once per Vault Blob Type and must not go and fetch one.
- Converge a Vault Meta through `convergeVaultMeta` (`src/lib/vault/vaultMetaConverge.ts`), and nowhere near a Vault Blob decision beyond the Vault Identity read named above. It takes `getVaultMeta` and nothing else, so it structurally cannot push a local wrapping over the server's and undo a passphrase change made elsewhere; adoption comes back as a next Local Vault for the caller to save. Adopting a remote wrapping is the one move that can brick a Local Vault and it never happens without an explicit answer ([ADR 0057](../../../docs/adr/0057-vault-meta-converges-separately-and-never-silently.md)).
- Push a local wrapping through `settleVaultMeta` / `changePassphraseWithCurrent` / `resetPassphraseAfterRecovery` / `rotateRecoveryKeyWithPassphrase` (`src/lib/vault/vaultMetaPush.ts`), never by calling `putServerVaultMetaEtagAware` at a new call site. A push is allowed on one condition and it is not "this device holds the Master Key" — the retry runs at session start against a locked Vault. It is that the server still holds the Vault Meta this device last agreed on, which the Vault Meta Bookmark is what proves. A moved server is refused and left for `convergeVaultMeta` to ask about at session start, never merged and never prompted mid-flow ([ADR 0060](../../../docs/adr/0060-a-device-may-push-a-wrapping-it-wrote-over-a-server-it-can-prove-has-not-moved.md)).
- Name a passphrase change by what authorizes it. `changePassphrase` verifies the current passphrase and `resetPassphrase` does not, because a User who has just unlocked with a recovery key cannot supply the one they forgot. They are two methods rather than one with an optional field: a check that can be skipped by leaving a property out is not a check ([ADR 0053](../../../docs/adr/0053-a-fan-out-over-a-domain-enum-is-pinned-at-its-call-site.md)).
- Rotate a Recovery Key in two calls — `mintRecoveryKey` (`src/lib/vault/recoveryKeyMint.ts`), then `rotateRecoveryKeyWithPassphrase`. Nothing is written between them, which is what leaves the old key working for a User who abandons the flow after seeing the new one (CONTEXT.md, "Recovery Key Rotation"). Do not collapse them into one call taking a confirmation callback: a library raising the User-facing confirmation from underneath its caller is the shape ADR 0057 was written against.
- Validate a passphrase through `passphrasePolicy.ts` (`passphraseSchema`, `currentPassphraseSchema`, `newPassphraseSchema`, `changePassphraseSchema`), never with a length check written at the call site. The rule was restated inline at each site that collected one, which is how three places came to own the same rule with nothing making them agree.
- Pass `onConflict` explicitly wherever `putServerVaultMetaEtagAware` is called. Its default raises a `window.confirm` from inside the library, which is the shape ADR 0057 was written against.
- Settle a Vault Meta before asking about one. A wrapping this device changed and could not push looks exactly like one changed elsewhere, so converging first tells a User their own change came from another device and offers them a button that reverts it.
- Validate ciphertext bundle shape and size before import.
- Reach a Local Vault through `createVaultHandle({ owner })` ([ADR 0047](../../../docs/adr/0047-vault-access-is-obtained-through-an-owner-bound-handle.md)). Storage is one entry per User, keyed by user id, with the owner written into the record.
- Claim an Unclaimed Local Vault through `claimUnclaimedLocalVaultOnEvidence` (`src/lib/vault/vaultClaimEvidence.ts`), never by calling `claimUnclaimedLocalVaultLocked` at a new call site. It is where the evidence is established and the one place that decides whether a claim happens — and it takes `getVaultMeta` and nothing else, so no answer given to it can write to the server. The four outcomes are distinct on purpose: a server that did not answer `postponed`s, and collapsing that into "no evidence" would hand the check's own off-switch to whoever can drop the network ([ADR 0061](../../../docs/adr/0061-vault-claim-is-proven-by-evidence-not-by-unwrap.md)).
- Send every `putVaultMeta` and `putVaultBlob` through `sendVaultWrite` (`src/lib/vault/serverVaultSync.ts`). It forgets the unconditional reads `shareInFlightVaultReads` is sharing, before and after the write; a PUT sent around it lets a read issued after the write join a request sent before it (#1489). A test in `serverVaultSync.sharedReads.test.ts` fails on an unwrapped call. Build a dashboard runner's api with `createSharedVaultApi(owner)`, not by wrapping `createVaultApi()` at the call site.
- Synchronise a save by giving the handle a `syncSink` (`createVaultSyncQueue`), never by pushing at a write call site. The handle is the only way to reach a Local Vault, so it is the only place a write cannot get past — a push added beside a call site is a push the next call site will not have.

## Do Not

- Do not send decrypted vault data to backend APIs.
- Do not persist master keys, passphrases, or recovery keys in plaintext.
- Do not remove the unsuffixed `myorganiser_vault_v1` slot, and do not promote it to an owned record without Vault Claim Evidence. It is an Unclaimed Local Vault: every outcome other than a claim must leave it byte-identical, and until a claim succeeds it is still where that Vault lives, so a write goes back to it.
- Do not treat a passphrase unwrap as proof that an Unclaimed Local Vault is this User's. Key derivation uses the Vault's own salt, so two people sharing a passphrase string each unwrap the other's Vault — an unwrap establishes knowledge of a string, not ownership ([ADR 0061](../../../docs/adr/0061-vault-claim-is-proven-by-evidence-not-by-unwrap.md)). There is deliberately no `claimUnclaimedLocalVault(passphrase)`; the one that existed is what made a shared passphrase enough to open somebody else's Vault.
- Creating a Vault is the one write that does not go back to it. `LocalVaultSlot.createNew` lands in that owner's own entry rather than following the read, because a User who declines an Unclaimed Local Vault and makes their own must leave the declined one exactly where it was. Routing creation through `write` instead would destroy it, which is the escape path in [#496](https://github.com/mnaimfaizy/myorganiser/issues/496).
