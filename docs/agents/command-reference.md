# Command Reference

The on-demand command catalogue for the root [Agent Guide](../../AGENTS.md#commands). The everyday commands — build, test, e2e, lint, format, AI commit, AI PR, OpenAPI sync, Prisma, and `yarn gates:run` — live there and are not restated here. Each command is documented once: add a new gate, measurement, or tool command to this file, not to `AGENTS.md`.

## Release

- Release (cut branch): `yarn release:cut --version vX.Y.Z --push --notes-file RELEASE_NOTES.md`.
- Release (tag after production deploy): `yarn release:tag --version vX.Y.Z --push`.
- Release dry-run (preview only): `yarn release:cut --version vX.Y.Z --dry-run`.

## Sub-agents and Skills

- Sub-agent sync check: `yarn agents:sync:check`.
- Sub-agent sync apply: `yarn agents:sync`.
- Sub-agent model/catalog audit: `yarn agents:models:audit`.
- Sub-agent model audit contracts (retirement-table reader): `node --test tools/scripts/lib/model-retirements.test.ts`.
- Sandcastle loop usage summary: `yarn agents:usage:report`.
- Committed Upstream Brief reports: `yarn upstream:briefs:check` (a thin wrapper over the skill's own gate, `.agents/skills/upstream-brief/check-reports.mjs`: it fails on an adapter problem in `upstream-brief.config.yml`, re-validates every structured `*.json` report committed under the brief directory against the commit the report itself records, and checks every declined Opportunity; `yarn upstream:briefs:test` runs every suite in the skill folder, including `portability.test.mjs`, which copies the folder alone into an empty repository and runs it there; the wrapper's own suite runs in `yarn tools:test`). See [ADR 0084](../adr/0084-an-upstream-brief-is-anchored-to-what-is-installed-and-accepted-on-checked-evidence.md) and [ADR 0018](../adr/0018-upstream-brief-portable-instruction-audit.md); shape and memory in [REPORT.md](../../.agents/skills/upstream-brief/REPORT.md), [LEDGER.md](../../.agents/skills/upstream-brief/LEDGER.md), and [SKILL.md](../../.agents/skills/upstream-brief/SKILL.md).

## Repository structure and Nx

- Root README check: `yarn readme:check`.
- Nx project tags check: `yarn nx:tags:check` (asserts every `project.json` carries exactly one `type:*`/`scope:*`/`tier:*` tag from `tools/config/nx-project-tags.json`). See [ADR 0070](../adr/0070-a-review-tier-is-a-fact-about-the-diff-and-a-gate-tier-is-a-decision-about-the-work.md).

Every project's `typecheck` target is inferred by `tools/scripts/nx/typecheck-plugin.ts`, so `yarn nx run <project>:typecheck` and `yarn nx affected -t typecheck` work for one project or one branch. See [ADR 0141](../adr/0141-typecheck-is-a-cached-per-project-inferred-target.md).
- Nx declared-target ratchet check: `yarn nx:targets:check` (asserts every `project.json` target on a deprecated `@nx/*` executor matches the shrink-only baseline `tools/config/nx-declared-targets-baseline.json`; `node --test tools/scripts/check-nx-declared-targets.test.ts` covers it). See [ADR 0082](../adr/0082-nx-targets-are-inferred-and-a-declared-target-is-migration-debt.md) and [ADR 0083](../adr/0083-a-declared-target-is-debt-only-on-an-executor-nx-deprecated.md).

See [ADR 0115](../adr/0115-a-concurrency-group-agrees-with-the-job-it-cannot-see.md).
- Review checklist check: `yarn review:checklist:check` (asserts [`docs/review/REVIEW_CHECKLIST.md`](../review/REVIEW_CHECKLIST.md) agrees with `tools/config/review-obligations.json` on ids, order, and fields; `--print` shows both sides).

- Rule catalogue check: `yarn review:rules:check` (asserts `tools/config/review-rules.json` agrees with the finding contract, the obligations catalogue, and the ids each axis's brief file beside [the code-review skill](../../.agents/skills/code-review/SKILL.md) offers its sub-agent, and that the two briefs carry the same shared block; `--print` lists the catalogue, `yarn tools:test` covers the loader). See [ADR 0071](../adr/0071-a-finding-blocks-only-on-evidence-and-a-verdict-is-computed-never-written.md).
- Reviewer tool allowlist check: `yarn review:allowlist:check` (asserts every command the code-review skill or [the Review Checklist](../review/REVIEW_CHECKLIST.md) instructs is permitted by `.github/actions/code-reviewer/action.yml`'s `--allowedTools` and not intercepted by an `ask`/`deny` rule in tracked `.claude/settings.json`, and that every path-scoped file grant there is anchored and on a tool Claude Code consults; `--print` shows every entry and rule, `node --test tools/scripts/check-review-tool-allowlist.test.ts` covers the matcher). See [ADR 0099](../adr/0099-a-project-ask-rule-is-a-refusal-in-a-headless-run.md), [ADR 0118](../adr/0118-a-file-grant-is-anchored-where-the-session-started.md), and [the run-45 research brief](../research/2026-09-10-the-answer-sheet-is-inert.md).
- Code review golden set: `yarn review:golden:check` (asserts `tools/config/review-golden-set.json` is well-formed and reachable from `main`, and matches the replay's trigger, tier, and pre-score obligation-gate rules; `yarn review:golden:score --case <id> --normalized <file>` scores one replay). See [ADR 0109](../adr/0109-a-golden-replay-runs-on-a-schedule-and-on-request.md), [ADR 0102](../adr/0102-a-golden-replay-reviews-the-case-tree-with-the-pull-requests-harness.md), [ADR 0072](../adr/0072-a-golden-case-earns-its-replay-frequency.md), [ADR 0116](../adr/0116-a-golden-case-stands-on-its-catch-rate-over-its-last-ten-scored-runs.md), [ADR 0074](../adr/0074-a-gate-suppresses-a-finding-only-if-something-runs-it.md), and [ADR 0101](../adr/0101-a-replay-whose-answer-sheet-fails-its-check-measured-nothing.md); results are kept current in [`docs/review/golden-replay-results.md`](../review/golden-replay-results.md).
- Code review escaped-defect rate: `yarn review:escaped:measure [--days 60]` (of the Pull Requests the reviewer passed, what fraction a later fix names as root cause; `yarn tools:test` covers the attribution parser). Not a gate; opt-out in `tools/config/gate-coverage-optout.json`. See [ADR 0077](../adr/0077-an-escaped-defect-is-one-the-reviewer-saw-and-passed.md); kept current in [`docs/review/escaped-defect-rate.md`](../review/escaped-defect-rate.md).
- Fix attribution check: `yarn fix:attribution:check --base <sha> --head <sha> --branch <ref> [--title <text>]` (asserts a fix's commits carry `Introduced in #<pull request>` or a named `unknown` reason; `node --test tools/scripts/check-fix-attribution.test.ts` covers it). See [ADR 0100](../adr/0100-a-fix-names-what-introduced-it-in-its-commits.md).
- Code review effective-false-positive rate: `yarn review:noise:measure [--days 30]` (per rule, the share of findings raised and still unaddressed on the next push; `--save-gather` persists the 30-day evidence window; `yarn tools:test` covers the classes, marker, and budget). Not a gate; opt-out in `tools/config/gate-coverage-optout.json`. See [ADR 0079](../adr/0079-an-effective-false-positive-is-a-finding-nobody-acted-on.md); kept current in [`docs/review/effective-false-positive-rate.md`](../review/effective-false-positive-rate.md).
- PR CI duration: `yarn ci:duration:measure [--days 14]` (how long a pull request waited for CI, computed from Actions API job and step timestamps with linear-interpolated percentiles: p50 and p90 for all pull requests and for **Single-Library Pull Requests**, the share of runs each check finished last, the stale-branch share (reported, not a signal), the Pull Requests merged while `main` had moved past their head, and the five revisit signals — each naming the decision ticket to reopen. `--save-gather` persists the window and `--gathered` re-measures it, `--out`/`--json` write the report; `yarn tools:test` covers the percentiles, the classification, each signal, and the ten-run cutoff). Not a gate; opt-out in `tools/config/gate-coverage-optout.json`. `.github/workflows/pr-ci-duration-watch.yml` runs it weekly and reports a breach on the fixed-title issue `[automation] PR CI is over its five-minute target`, recording the recovery once; a window with fewer than ten Single-Library runs is "not enough data" and opens nothing. The judgments are pure in `tools/scripts/lib/ci-duration.ts` and `tools/scripts/lib/ci-duration-watch-issue.ts`. The `merged-behind-main` signal (target 0) replaced the 10% stale-run share; see [ADR 0144](../adr/0144-a-batch-of-pull-requests-merges-through-the-merge-train-not-the-admin-bypass.md).
- Merge Train: `yarn merge:train <pr>… [--method merge|squash|rebase] [--poll 30] [--timeout 45] [--dry-run] [--auto]` (merges Pull Requests into `main` one at a time in the order given: brings a branch up to date when `main` has moved past it, waits for every required check of `main`'s ruleset on the new head, then merges exactly that head with `--match-head-commit` and never `--admin`. Stops at the first red required check, conflict, draft, required review, or a Pull Request still waiting after `--timeout` minutes, and names the ones it never reached; exit 0 when all merged, 1 when it stopped, 2 when it could not start. `--dry-run` reads each Pull Request and says what it would do. The decisions are pure in `tools/scripts/lib/merge-train.ts`; `yarn tools:test` drives the whole loop over a fake GitHub). Not a gate: it changes GitHub, never the tree. The way a batch of Standalone Runs merges; see [ADR 0144](../adr/0144-a-batch-of-pull-requests-merges-through-the-merge-train-not-the-admin-bypass.md). `yarn merge:train --auto <pr>… [--dry-run]` is Auto-merge ([ADR 0148](../adr/0148-the-merge-train-auto-merges-only-on-facts-it-reads-for-the-head-it-merges.md)): it decides each candidate from facts read for its head and never stops at one, listing a held candidate with its reason and moving on. `main`'s CI is read once per pass, so a red `main` holds the whole pass while the pass's own merges hold nothing after them (each is still gated by its own required checks). Only `**Door:** one-way` holds, a Door field in another form holds as "Door line unreadable", and no Door line changes nothing. The Review Tier, Agent Verdict and QA Report have no reader yet and hold. The mode is `tools/config/merge-train-auto-merge.json` (`off` / `shadow` / `on`, shipped `shadow`, missing or invalid reads `off`), a `review:human` path under `tools/config/**`. `off` writes nothing; `shadow` keeps one comment per candidate, marked `<!-- merge-train:auto-merge -->` and edited in place, saying "would auto-merge at `<sha>`" or "held: <reason>"; `on` merges through the hand-started train's own loop; `--dry-run` writes nothing. Exit 0 when the pass finished, 1 when a shadow comment could not be written, 2 when it could not start.
- Code review report contract: `yarn review:validate <report.json> --out <normalized.json> [--previous <normalized.json>] [--facts <run-facts.json>] [--worklist <obligations.json>]` rejects or normalizes a `/code-review` report, computes its verdict, and carries each finding's id forward from the previous report; `yarn review:render <normalized.json>` renders the two-section Markdown; `yarn tools:test` runs the contract tests. See [ADR 0071](../adr/0071-a-finding-blocks-only-on-evidence-and-a-verdict-is-computed-never-written.md).
- Code review run facts: `node tools/scripts/review/read-transcript-facts.ts <execution-file> --out <run-facts.json> [--index CODING_STANDARDS.md]` reads a reviewer transcript for the standards documents the Standards sub-agent opened, the commands the sub-agents ran, the session's duration, token figures, model and Claude Code CLI version, and whether each dispatch was the skill's template; `yarn review:validate --facts <run-facts.json>` overwrites the report's own claims with them and judges the run: no sub-agent reading an axis's brief, or a reported finding no sub-agent returned, is recorded as a failure that fails `Agent Review Ran` and voids a golden replay, while an unopened `CODING_STANDARDS.md`, a dispatch off the template, or a transcript or reply that cannot be read tightens the Review Tier one step. The reader itself gates nothing; a transcript it cannot read is recorded as unknown, never as an empty list. `yarn tools:test` covers both against fixtures cut from real transcripts. See [ADR 0123](../adr/0123-a-review-reports-facts-about-its-own-run-are-read-from-the-transcript.md).
- CI code review: `.github/workflows/code-review.yml` runs the `/code-review` skill as two checks — `Agent Review Ran` (pipeline facts, eligible to be required) and `Agent Verdict` (a judgment on the diff, permanently advisory). Triggers automatically per the `CODE_REVIEW_MODE` repository variable (`CODE_REVIEW_ENABLED=false` disables it), or on demand via the `agent-review` label, a `/code-review` comment, or `workflow_dispatch`; needs `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`. See [ADR 0070](../adr/0070-a-review-tier-is-a-fact-about-the-diff-and-a-gate-tier-is-a-decision-about-the-work.md) item 6, [ADR 0071](../adr/0071-a-finding-blocks-only-on-evidence-and-a-verdict-is-computed-never-written.md), [ADR 0073](../adr/0073-a-required-check-is-a-fact-about-the-pipeline-not-a-judgment-about-the-diff.md), [ADR 0078](../adr/0078-a-citation-that-does-not-match-its-source-is-a-fact-about-the-pipeline.md), and [the token-scoping research brief](../research/2026-09-07-resolve-review-thread-token.md).

## QA tooling

- QA scenario grading: `yarn qa:grade --input <file.json | ->` (reads `{ "changeKind": "fix" | "feature", "scenarios": [{ "id", "before": "pass" | "fail" | "not-run" | "cannot-run", "after": "pass" | "fail" | "cannot-run" }] }` and prints each scenario's result — PASS, FAIL: regression, FAIL: pre-existing, Not proven or Left for a person — with the QA Report headline, a `maintainerDecision` flag on every FAIL: pre-existing; exit 0 = graded and the headline is not QA failed, 1 = QA failed, 2 = bad invocation, malformed input, or a scenario that failed After with Before `not-run`, which is refused with "re-run on the merge-base first" rather than graded. Where ADR 0147 is silent it fails toward the louder result: an After failure whose Before cannot run is a regression, and an After that cannot run is Left for a person). The logic is `tools/qa/lib/grade-scenarios.ts`. See [ADR 0147](../adr/0147-a-qa-plans-scenarios-are-scripted-and-run-on-the-code-before-and-after-the-change.md).
- QA stack: `yarn qa:stack:start --worktree <path> --change-kind fix|feature --merge-base <sha> --head <sha> [--with-before | --before-only] [--database-url <url>]`, `yarn qa:stack:stop`, `yarn qa:stack:status`. Start brings up web on `http://localhost:4300`, the backend on `3300` and its own Postgres container (`myorganiser-qa-db`, the `docker-compose.yml` image) on `127.0.0.1:5499` — never the Maintainer's 4200/3000/5453 — from a linked worktree: it checks out the first side it serves, migrates forward, generates the Prisma client, seeds the QA Accounts once (`qa-accounts.ts seed --restore`), starts both services, and checks the served commit. It serves Before then After for a fix, After only for a feature, Before then After for a feature with `--with-before` (a scenario claims existing behaviour still works), and Before only with `--before-only` (a feature's merge-base re-run after an After failure, on a fresh stack). It refuses, with exit 1 and before any step, a database that is not local (the QA Account tooling's `localDatabaseRefusal`, reused unchanged and with no override; `--database-url` swaps the container for another local database; a shell whose own `NODE_ENV` is production is refused too, since the stack's env always says development), the repository's primary checkout, a worktree with uncommitted changes other than `next dev`'s rewrite of `apps/web/AGENTS.md`, a port in use, a stack that is already up, and a merge-base that is not an ancestor of the head. The environment is built from the worktree's `.env.example` with generated local-only secrets, never from a person's env file, and written with the state to `tmp/qa/stack/` (`state.json`, `env.sh`, `backend.log`, `web.log`). Stop kills only the process groups the stack recorded and removes only its own container. Status exits 0 when the stack is up and serving its current side, 1 otherwise. Exit 2 = bad invocation or a missing dependency (docker, `lsof`, `.env.example`). The rules are `tools/qa/lib/qa-stack.ts` and `tools/qa/lib/qa-switch.ts`; the steps run in `tools/qa/lib/qa-stack-executor.ts`. See [ADR 0147](../adr/0147-a-qa-plans-scenarios-are-scripted-and-run-on-the-code-before-and-after-the-change.md).
- QA Before/After switch: `yarn qa:switch --worktree <path> --to before|after` (moves the running QA stack to the merge-base or the head, planned and checked before a step runs: stop the services, check out, install when `yarn.lock` differs, migrate forward with `prisma migrate deploy`, start the services, check the served commit; never re-seeds, so Before and After share the QA Accounts' data; moving to the side already served only re-checks it; a switch back to Before after After is refused with exit 1 rather than rolling the database back — stop the stack and start a fresh one with `--before-only`). **Served-commit check** — neither the backend nor web exposes the commit it runs, so the check is at the process level, and it passes only if all hold: the worktree's `HEAD` is the expected commit; it has no uncommitted change other than `apps/web/AGENTS.md`; and for both backend and web, the recorded process group is alive, it is the process group listening on the service's port, and it was spawned while `HEAD` was the expected commit. Any miss exits 1 naming each one, and no scenario may run. Exit 0 = serving the side asked for; 1 = a refusal (as `qa:stack:start`'s worktree refusals, or a different `--worktree` from the stack's), a failed step, or a mismatch; 2 = bad invocation. The built-in browser reaches the stack through the `qa-web` attach entry in `.claude/launch.json` (`http://localhost:4300`, no command, so it starts no second server).
- QA combine: `yarn qa:combine --before <file> --after <file> --out <path without extension> [--height <even px, default 720>]` (combines a Before/After pair into one QA Artifact: two screenshots, `.png`/`.jpg`, give `<out>.png`, one side-by-side image; two videos, `.webm`/`.mp4`/`.mov`, give `<out>.mp4`, one side-by-side video held to the last frame of the longer side, and `<out>.gif`, a preview kept under 2 MiB by trying smaller sizes and frame rates until one fits. Each side carries a "BEFORE" or "AFTER" label drawn by the tool itself, so it does not depend on ffmpeg's `drawtext`. It prints the files as JSON. Exit 0 = combined; 1 = ffmpeg failed, or no GIF fits the cap (nothing is left behind); 2 = bad invocation, a missing input, mixed kinds, or ffmpeg not on `PATH` — it names the install command and never reports a result. It wraps the system ffmpeg, which is not an npm dependency. Combining is not uploading: the pure upload-eligibility rule is `tools/qa/lib/upload-eligibility.ts`, stated in [Uploading QA Artifacts](../../.agents/skills/finish-standalone-runs/SKILL.md#uploading-qa-artifacts).) `QA_REQUIRE_FFMPEG`: the suite's one real-ffmpeg test (`tools/qa/qa-combine.real-ffmpeg.test.ts`) skips with a visible reason when ffmpeg is absent and this variable is unset, and fails when it is set; CI's `QA tooling contracts` step installs ffmpeg and sets it, so CI always runs the real test. The rules are `tools/qa/lib/qa-combine.ts` and `tools/qa/lib/qa-label.ts`; the steps run in `tools/qa/lib/qa-combine-executor.ts`. See [ADR 0147](../adr/0147-a-qa-plans-scenarios-are-scripted-and-run-on-the-code-before-and-after-the-change.md).
- QA Request Transcript redactor: `yarn qa:redact --input <file.json | ->` (reads the calls a scenario made and what came back, `{ "scenarios": [{ "id", "calls": [{ "side": "before" | "after", "request": { "method", "path", "query"?, "headers"?, "body"? }, "response": { "status", "headers"?, "body"? } }] }] }`, and prints one collapsed `<details>` block ready for the QA Report. Every field is allow-listed by name: a safe field passes through unchanged; a credential, cookie, token or authorization field is withheld as `[withheld]` (its whole subtree; a Bearer or JWT-shaped string, or a string containing a JWT piece, is withheld whatever its field); Ciphertext is shortened to an 8-character prefix and its length. A URL-typed string (`path`, `query`, `location`, or anything starting `/`, `?`, `#` or `scheme://`) is decoded, at most 5 passes, and its `? # & ;` parameters are judged by name against the same allow-list: a safe name keeps its value, a credential name has its value withheld, any other name (including `amp` from `&amp;`) refuses, as does a string still decoding after the cap, and any `@` (also `%40`, `＠`) in a URL-typed string at any decode level, which is refused wherever it sits and never rewritten: userinfo cannot be parsed reliably, so a legitimate `@` in a URL refuses too. A form-encoded string body (`body: "a=b&…"`) is out of scope: the web client sends JSON, and JSON bodies are covered. A credential-word field that is not a clean name (for example a key `token=V`) prints as `<field #n>`. Every string is first NFKC-normalised and stripped of Unicode format characters (zero-width and similar), at every decode level, so look-alike `@` and `%` and hidden characters do not evade a check. Spaced text in non-URL fields is not parsed. Any other field refuses the whole transcript, nested and inside arrays too: stderr names where each problem is, never a value or an unrecognised name: `<path> key #n` for an unknown field, `<path> parameter #n` for an unknown URL parameter (n is its position; look in the input to see which), and stdout stays empty. Exit 0 = rendered, 1 = refused, 2 = bad invocation or malformed input. It does not capture traffic: the caller supplies the calls. To allow a new field or parameter name, add it to the allow-list in `tools/qa/lib/redact-transcript.ts`). The rules are `tools/qa/lib/redact-transcript.ts`; the same withhold-on-violation, never-print-a-value pattern as the Host Apply log scanner. See [ADR 0147](../adr/0147-a-qa-plans-scenarios-are-scripted-and-run-on-the-code-before-and-after-the-change.md).
- QA scenario runner: `yarn qa:run --worktree <path> --change-kind fix|feature --merge-base <sha> --head <sha> --scenarios <dir under tmp/qa/> --out <dir under tmp/qa/> [--with-before]` (plays a QA Plan's scenario scripts in real Chromium through the existing `@playwright/test` dependency and ties the QA tooling together. Each `*.ts` in `--scenarios` default-exports `{ id, capture, run }`: `capture` is the plan's `Capture:` line (`video`, `screenshot`, `transcript` or `none`), and `run({ page, baseURL, side, account, cannotRun })` passes by resolving, fails by throwing, and ends as cannot-run through `cannotRun(reason)`; `account(id)` gives a QA Account's sign-in values, so both sides sign in alike. The runner starts the QA stack itself (`qa:stack:start`, so it refuses what that refuses), and runs every scenario on Before, then `qa:switch --to after`, then every scenario on After for a fix or a feature run `--with-before`; a feature runs After only and, when a scenario fails, stops the stack, starts a fresh one with `--before-only` and re-runs only the failed scenarios on the merge-base. A start or switch that fails closed means no scenario runs on that side. Every run uses a fresh context at 1280×720, always records a video, a final screenshot and the calls it made to the QA backend (method, path with query, status, bodies; never headers), and keeps only what `capture` asks for in `<out>/before/` and `<out>/after/`; a failed run's video is kept whatever the line says: in `<out>/local/`, never offered for upload, or, when the line is `video`, as that side's QA Artifact in `<out>/<side>/`. Then it grades with `qa:grade`'s rules, combines each Before/After screenshot or video pair with `qa:combine` into `<out>/combined/`, and redacts each `transcript` scenario's calls with `qa:redact`'s rules into `<out>/transcripts/<id>.md`; a refused transcript writes its raw calls to `<out>/local/<id>.calls.json` and names only the refused paths. `<out>/run.json` lists each scenario's outcomes, result, files and problems, marks each file `uploadEligible` (only a combined file can be; `local/` files and transcripts never are), and gives the headline. The stack is left up for judgement checks through the `qa-web` launch entry; stop it with `yarn qa:stack:stop`. Exit 0 = graded and not QA failed, with every kept file made; 1 = QA failed, the stack or a switch failed closed, or a recording, combined file or transcript could not be made; 2 = bad invocation, `--scenarios` or `--out` outside `tmp/qa/`, a malformed scenario script, or Chromium (`corepack yarn playwright install chromium`) missing, or ffmpeg missing when a scenario's `Capture:` is `video` or `screenshot` (a run of only `transcript` and `none` combines nothing and does not need it), all checked before the stack starts; a stack start, switch or stop that itself exits 2 (a bad invocation or a missing dependency such as docker) passes its 2 through. Scenario scripts stay in `tmp/qa/` and are never committed. The rules are `tools/qa/lib/qa-run.ts`; the steps run in `tools/qa/lib/qa-run-executor.ts`, and the browser in `tools/qa/lib/qa-run-browser.ts`. See [ADR 0147](../adr/0147-a-qa-plans-scenarios-are-scripted-and-run-on-the-code-before-and-after-the-change.md).
- QA tooling suites: `yarn qa:tools:test` (every `tools/qa/**/*.test.ts` under `node --test`; its own CI step and gate, beside `tools:test` rather than inside its glob) and `yarn qa:tools:typecheck` (`tsc -p tools/qa/tsconfig.json --noEmit`, its own program and CI step). The pre-commit hook runs both when anything under `tools/qa` is staged.
