Before you approve

The run may have been queued the instant the release branch was created, before CI finished on release/vX.Y.Z. Check CI on that branch yourself — nothing in this pipeline checks it for you (dispatch-production-deploy.yml:7, :19, :93-101; ADR 0028, Consequences).

Before you Cut

A scheduled Staging upload cannot be Cut. Staging uploads once a day from the newest green main commit, and that run's name records no commit, so release:cut refuses it. Dispatch Deploy Staging in full — not apply_only — at the commit you mean to Cut. An apply_only dispatch after a scheduled upload no longer satisfies the guard (deploy-staging.yml:19, :243-260; ADR 0128, Consequences).

← → step · Space plays
ci
Authoritative Lockfile Policy → Secure Install Review → Prepare Dependency Cache → Chromatic + Setup Affected Context → Lint + Test → Build Backend / Build Frontend (ci.yml). Which target ran on which project, and why a red one blocks in one mode and only reports in another, is docs/sandcastle/gates.html and ADR 0012 — this page treats the whole thing as one pass/fail box on purpose.
staging
Two triggers: schedule at 0 16 * * * — 16:00 UTC — and workflow_dispatch (deploy-staging.yml:21-26). It no longer deploys when CI goes green on main. The first job, select (:73), picks the commit. A dispatch always deploys the dispatched commit. On a schedule it takes the newest main commit whose CI succeeded (:122-124) and then decides, from what Staging's web app and its backend uploads already hold (decideSchedule, :45-64, :140-142), among three kinds of result. Proceed with that commit. Stop, green: the commit predates the Staging web deploy; Staging already serves it; or the web app or the backend holds a newer commit that a dispatch put there — the schedule never rolls Staging back. Fail without uploading: the web address did not answer (no answer is not evidence that Staging is empty); Staging serves the commit but /sw.js lacks its two headers; or the commit is already uploaded by an earlier run, as the web bundle or the backend, and the web app is not serving it. Nothing is uploaded on any stop or failure. For that last failure, when an install is owed the operator clicks “Run NPM Install” then “Restart” in cPanel first; a full dispatch helps only when a restart did not take, because with an install owed it would fail again. Never near production — see panel 2. Uploaded is not applied: host-apply runs only on workflow_dispatch (:280, :282), so a scheduled run uploads the backend bundle and deploys the web app, but nothing applies the backend — it writes a “Backend uploaded by the schedule, not applied” notice to the job summary instead (:243-260). The run name carries the commit only on a dispatch (:19), and the Cut step reads the uploaded commit from that name, so it refuses a scheduled upload: only a full dispatch (upload and Host Apply) satisfies it.
cut
The one human choice on this whole spine before the halt: when to run it. release:cut checks out main, confirms it is clean and up to date, and then refuses unless Staging already holds this exact commit, Host Applied: its latest successful upload (deploy-backend) must be this commit, and a successful host-apply at this commit must have started after that upload landed. There is no flag to skip this. Only then does it create + push release/vX.Y.Z (package.json:26, release.mjs:604, :632-641). The commit is read from the upload run's name, and a scheduled run's name carries none (deploy-staging.yml:19), so the Cut refuses a scheduled upload until a full dispatch of Deploy Staging uploads and applies the commit; apply_only after a scheduled upload does not satisfy it. When the upload came from a dispatch and only host-apply is missing or older, apply_only is still the next step (staging-host-apply-guard.ts, ADR 0056, amendments 2026-09-14 and 2026-10-13; ADR 0128). release:cut has no --tag flag — cutting cannot tag.
releasepr
Fires on push to release/v* (release-pr.yml:6-8). Opens or reuses a PR to main and tries to enable auto-merge (:105-117). Simultaneous with, and independent of, the production dispatch below — the same push causes both.
dispatch
Fires on create of a branch matching ^release/v[0-9]+\.[0-9]+\.[0-9]+$ (dispatch-production-deploy.yml:7, :19). It calls createWorkflowDispatch against deploy-production.yml (dispatch-production-deploy.yml:93-101) and nothing else — its own job never runs a deploy step. Its previous name, Deploy Production (latest release), read as though it did; that misreading is why it was renamed (ADR 0028, Consequences). No step in this chain, or in the workflow it dispatches, checks whether CI is green on the branch it just created.
prodstart
The workflow file is literally named Deploy Production (manual) (deploy-production.yml:1) and its only trigger is workflow_dispatch (:5-6) — a workflow just dispatched it automatically, one node back. The word “manual” in the name describes the approval gate two steps ahead, not how the run started.
validate
Rejects any github.ref that is not refs/heads/release/* (deploy-production.yml:42-52) — that guard accepts release/anything, not only semver. Timeout 5 minutes (:31). Then resolves release_ref: the explicit release_branch input if that branch exists on origin (:63-71), otherwise the newest release/vX.Y.Z by sort -V (:73-87). Panel 3 has the full asymmetry between this ref and the one each job actually checks out.
offrepo
The single thing that makes this workflow manual: the production GitHub Environment's required-reviewer rule. It lives in repository settings, not in any file this diagram — or git grep — can show you. Every workflow file reads exactly the same with or without it, and it is removable without a pull request (ADR 0028). Verify it directly: gh api repos/mnaimfaizy/myorganiser/environments/production --jq '.protection_rules'.
halt
deploy-backend (deploy-production.yml:130), host-apply (:183), and deploy-frontend (:295) all declare environment: production — three deploy jobs, one approval batch. A fourth job, mark-feedback-release (:373), also declares it but does not join the batch: it needs host-apply and deploy-frontend (:369), so it only becomes ready after both succeed and raises its own, second approval prompt. Nothing else marks a job as gated. Everything upstream of this box happened without anyone deciding anything; everything downstream needs the sign-off this box represents. Choose an outcome below to continue the walkthrough.
deploybackend
Packages with yarn package:backend:api and ships ./dist/deploy/backend-api/ over FTP to cPanel, using a production backend FTP credential distinct from staging's (deploy-production.yml:164-172). Timeout 45 minutes (:129), FTP transfer timeout 300000 ms — the same figure staging and the frontend job both use.
hostapply
Runs after deploy-backend succeeds, or on an apply_only re-dispatch, and is itself gated on environment: production — a third job behind the same approval as deploy-backend and deploy-frontend. Over SSH with a deploy key it activates the environment's Node virtualenv, loads DATABASE_URL from the host's Node.js selector store — never a GitHub secret — then runs npm ci --omit=dev → prisma migrate deploy → prisma generate → touch tmp/restart.txt → prisma migrate status, all under set -euo pipefail (deploy-production.yml:178-288): the first failing step stops everything after it — no rollback, no migrate-down, no “restart anyway,” no Tag (ADR 0056). Verified with two HTTP probes (:271-288): GET {API_ORIGIN}/docs must be 2xx, and a cron POST carrying a deliberately wrong secret must be exactly 401. This page names the algorithm and the secret names only — never the host, port, user, or path values themselves, per ADR 0056.
deployfrontend
Packages with yarn package:web and ships ./dist/deploy/web/ over FTP to cPanel (deploy-production.yml:346-363). The job ends at the upload; Staging's frontend job goes on to restart the app and probe it — see panel 2. Runs alongside host-apply, not after it — its needs: lists deploy-backend, not host-apply (:292), since neither job needs the other.
markrelease
Added after the deploy jobs, as the comment above it says (deploy-production.yml:365-367): once the Release is live, mark the Feedback Reports its commits fixed. It needs: validate, host-apply and deploy-frontend (:369), so it runs only after both succeed; it is skipped on an apply_only run (:370); it declares environment: production (:373), so approving the first batch does not approve it — a second prompt appears once the deploys are done. Timeout 10 minutes (:372). It collects the issues closed by Closes, Fixes or Resolves #N in the commits since the previous vX.Y.Z tag and POSTs them to the backend, which marks each Planned Feedback Report on those issues Fixed or Shipped and sends Fix Notices (ADR 0133). If it fails, the Release stays live and the reports stay Planned; Re-run failed jobs retries it alone and marks nothing twice. It needs FEEDBACK_RELEASE_SECRET on the production GitHub Environment (CI_CD_AND_RELEASE_PROCESS.md, section Release marking (Production)).
tag
Asserts it is on the release branch and up to date with origin, and that package.json matches the tag (release.mjs:757-759); refuses an existing tag (:761-763); creates no commit and writes no files (package.json:27). A commit here would move the branch past the exact SHA CI verified and a reviewer approved. vX.Y.Z existing means that version reached production.
publish
Triggered by the push of a tag matching ^v[0-9]+\.[0-9]+\.[0-9]+$ (publish-github-release.yml:6-8, :37). Reads RELEASE_NOTES.md from the tagged commit and creates or updates the GitHub Release, so re-running it is safe (:97-118).

2 · Staging is not a rehearsal of production

the two environments do not have the same shape

Both environments ship both bundles the same way: by FTP to cPanel. What differs is what surrounds the upload. Staging runs on a schedule with no approval, and a scheduled run that finds the commit uploaded but not running fails rather than re-uploading; its frontend job also restarts the web app and probes it, where Production's frontend job ends at the upload.

The Staging web app is not Host Applied: Host Apply stays backend-only and operator-dispatched. Its restart is a file upload, and the job in order does this:

  1. Checks out the tip's tools/scripts into .deploy-tools deploy-staging.yml:427-433, so the workflow's steps and the deploy script always come from the same commit while the bundle is built from the selected commit; every script step below runs .deploy-tools/….
  2. Asserts the web address and the API address share a parent domain, because the Session's refresh cookie is not sent across sites; the deploy-pipeline gate asserts the step is present (stagingAssertsSameSite) deploy-staging.yml:496-500.
  3. Builds the bundle with yarn package:web, setting the commit as the build id :502-512.
  4. Plans: restart, or install-owed when the bundle's dependency list differs from the list known to be installed, or when nothing is known yet (the first deploy to a host) :518-532.
  5. Uploads the bundle by FTP :536-544.
  6. On restart: uploads tmp/restart.txt :562-581, then probes until the running process answers with the uploaded commit and the service worker's Cache-Control and Content-Security-Policy equal their exact expected values :587-596.
  7. Otherwise it does not restart and fails: “Run NPM Install” and “Restart” are owed in cPanel :604-617. The next run confirms it.

3 · Which ref actually ships

deploy-production.yml

The branch you launch the run from and the branch that deploys can differ. Rendered as written, not editorialised.

  1. validate rejects any github.ref that is not refs/heads/release/* — note this guard accepts release/anything, not only semver. :42-52
  2. It resolves release_ref: the explicit release_branch input if that branch exists on origin :63-71, otherwise the newest release/vX.Y.Z by sort -V :73-87.
  3. The four job guards (prepare-dependencies, deploy-backend, host-apply, deploy-frontend) test github.ref :90, :126, :180, :291 — the ref the run was launched against. host-apply's guard also gates on needs.deploy-backend.result == 'success' or inputs.apply_only, since it can run in apply-only mode when deploy-backend was skipped.
  4. The deploy jobs — prepare-dependencies, deploy-backend, host-apply, and deploy-frontend — check out release_ref :101, :137, :190, :302 — the resolved branch from step 2, which is not always the same string.

4 · The tag is a receipt

release.mjs

release:tag asserts it is on the release branch, up to date with origin, and that package.json matches the tag (release.mjs:757-759); refuses an existing tag (:761-763); and creates no commits and writes no files — a commit here would move the branch past the exact SHA that CI verified and a reviewer approved (:749-756). release:cut has no way to tag at all: there is no --tag flag. vX.Y.Z existing means that version reached production (ADR 0028). That is why tagging comes last, not first.

5 · Constants, with their scopes

collision check, run repo-wide
Node — three scopes, one floor

CI runners pin exactly '22.18' at every setup-node step across ci.yml, deploy-staging.yml, deploy-production.yml. The repo floor is >=22.18.0 (package.json:7). release.mjs refuses a major below 22 (release.mjs:22-30). Three scopes, one floor — not a single pinned number.

Staging schedule

0 16 * * *, which GitHub reads as 16:00 UTC (deploy-staging.yml:21-26).

FTP transfer timeout

300000 ms, the same value at five sites: staging backend (deploy-staging.yml:241), staging web app (:544) and its restart upload (:581), production backend (deploy-production.yml:172), production frontend (:363). host-apply has no FTP step and no site here — it applies over SSH, not FTP.

Job timeouts

validate 5 min (:31); staging jobs 30 min (deploy-staging.yml:79, :149, :189, :284, :402) — five now, including select and host-apply; production's three deploy jobs 45 min each (deploy-production.yml:129, :182, :294) — three now, also including host-apply — and the fourth approval-gated job, mark-feedback-release, 10 min (:372); dispatcher, release-PR and publish 10 min each.

Concurrency

Staging has no workflow-level concurrency: block any more — it moved to job-level groups (issue #567), split by whether the job writes to APP_ROOT. deploy-staging-apply (cancel-in-progress: false) covers deploy-backend and host-apply (deploy-staging.yml:195-197, :286-288) — the two jobs that land and then apply the bundle. A newer run queues behind them: it must not cancel an in-flight prisma migrate deploy (the one behaviour ADR 0056 rules out), and it must not FTP a fresh bundle into a tree that npm ci is still working in either. deploy-staging (cancel-in-progress: true) covers only prepare-dependencies (:150-152) — it touches no host, so a newer run still kills it in flight. deploy-frontend has its own group, deploy-staging-web, with cancel-in-progress: false (:409-411): its upload is FTP into a live app root, and a cancelled upload would leave half a bundle, so a second run queues. It is a separate group from the backend's because the web app has its own root and may deploy beside a Host Apply. Production is unchanged: one workflow-level group, deploy-production, cancel-in-progress: false (deploy-production.yml:20-23) — runs queue and are never cancelled, so host-apply already inherits that queuing without needing a group of its own.

Four branch/tag patterns, one set

Not the same strictness: refs/heads/release/* (deploy-production.yml:45); the release-branch pattern in two spellings, ^release/v[0-9]+\.[0-9]+\.[0-9]+$ (dispatch-production-deploy.yml:40, :55) and /^release\/v\d+\.\d+\.\d+$/ (release-pr.yml:36); ^v[0-9]+\.[0-9]+\.[0-9]+$ (publish-github-release.yml:37); and /^v?(\d+)\.(\d+)\.(\d+)$/ (release.mjs:151), which rejects prerelease input outright.
